# CRM клуба (PS5 / игровые кабинки)

> Этот файл — основное ТЗ и источник контекста для разработки. Перед изменениями прочитать его полностью.
>
> Статус: онлайн-MVP — React web подключён к Django/PostgreSQL, персональные session/CSRF логины, касса/склад/история/отчёты и P2P Uzcard/Humo с явным подтверждением кассиром. Реальная Telegram Business доставка требует credentials и проверки в клубе. Запуск и фактические ограничения: [docs/ONLINE_MVP.md](docs/ONLINE_MVP.md), [docs/P2P.md](docs/P2P.md). Mock остаётся отдельным демонстрационным режимом.

Целевые границы модулей, API, offline-синхронизация и модель данных описаны в [ARCHITECTURE.md](ARCHITECTURE.md). Правила разработки для агента — в [AGENTS.md](AGENTS.md).

## Цель

Сделать CRM для клуба с игровыми кабинками, кассой и продажей товаров. Система должна учитывать игровые сессии, заказы, оплаты, склад по партиям, расходы, смены кассира, себестоимость, маржу, прибыль и историю действий. Владельцу и управляющему нужен просмотр каждого счёта и финансовых операций.

Первая версия работает через интернет на временном VPS. Архитектура должна позволить позже перенести сервер в клуб и работать через локальную Wi-Fi сеть. При потере интернета клиентское приложение должно уметь временно сохранять кассовые действия локально и синхронизировать их после восстановления связи. Полноценный автономный режим всех интеграций в первой версии не обещан: Telegram/P2P уведомления требуют связи.

## Стек

- **Backend / API:** Python 3.12+, Django, Django REST Framework.
- **База данных:** PostgreSQL. Денежные значения хранить целыми сумами в UZS или точным decimal; не использовать float.
- **Web:** React + TypeScript + Vite, адаптивный интерфейс кассира и админки, PWA для установки и ограниченной работы без связи.
- **Android / iOS:** Expo + React Native + TypeScript, отдельный мобильный клиент поверх того же API. Общие типы и правила обмена держать отдельно от UI; мобильное приложение подключать после стабилизации API.
- **Контракт:** документированный REST API с OpenAPI; frontend сначала разрабатывать на типизированных mock-данных, затем подключить backend.
- **Запуск и перенос:** Docker Compose на VPS; конфигурация через переменные окружения; PostgreSQL backup/restore; без привязки бизнес-логики к VPS-провайдеру.
- **Интеграции:** отдельный адаптер источника P2P уведомлений из Telegram Business. Реализованы отдельные источники обычных переводов Uzcard/Humo, HMAC bridge, ожидаемые части и явное подтверждение кассиром. Реальная доставка Telegram Business требует проверки с credentials клуба: [docs/P2P.md](docs/P2P.md).

Новая полноценная CRM не должна возвращаться к модели «Telegram-бот как весь интерфейс». C++ для данного проекта не выбран: основной объём — веб/API, бизнес-правила и интеграции; Python и TypeScript дадут быстрее развивать сервер и два клиентских интерфейса.

## Зафиксированные требования

### Пользователи и права

- **Владелец:** полный доступ, настройки, пользователи, тарифы, цены, расходы, склад, отчёты и аудит.
- **Управляющий:** доступ к управленческим разделам в рамках назначенных прав, включая просмотр любого счёта, отчёты, каталог, тарифы и склад.
- **Кассир:** работа со счетами, кабинками, продажами, оплатами, сменой и расходами своей смены. Кассиру недоступно изменение себестоимости, цен и системных настроек.
- На одной смене работает один кассир и одна касса. Входы каждого сотрудника персональные; действия не должны записываться от имени общей учётной записи.
- Матрицу прав уточнить и зафиксировать до реализации чувствительных операций (возвраты, отмена оплаты, ручные корректировки склада).

### Кабинки, счета и таймер

- Счёт создаётся при приходе клиента. Бронирование и отдельное клиентское приложение не входят в первую версию.
- Сначала кассир создаёт счёт и выбирает кабинку/тип приставки, затем явно нажимает **«Запустить таймер»**.
- Таймер продолжает идти, когда кассир уходит со страницы счёта. Можно работать с несколькими активными счетами.
- Пока игровое время идёт, кассир может добавлять товары и редактировать состав счёта. Удаление товара/позиции, влияющей на деньги или склад, требует причины и попадает в журнал.
- Кассир нажимает **«Предчек» / «Закрыть время»**: таймер останавливается, счёт получает статус ожидания оплаты, но оплата ещё не подтверждена и счёт не считается завершённым.
- Если клиент продолжает играть после предчека, кассир может возобновить счёт с фиксацией события и времени.
- После получения всей оплаты кассир выбирает один или несколько способов оплаты и окончательно закрывает счёт. Счёт с недоплатой остаётся ожидающим оплаты.
- Цена, тариф и состав сохраняются в счёте как снимок на момент операции, чтобы последующие изменения прайса не меняли историю.
- Время считается по фактическим минутам. Тарифы настраиваются по типу кабинки/приставки (например, PS4 и PS5) владельцем или управляющим.
- Итог счёта округлять до ближайших 500 UZS; пример: 53 333 → 53 500. Округление применять к итоговой сумме, не округляя каждую минуту отдельно.
- При смене кассира активные игровые счета продолжают идти; передача этих счетов следующей смене фиксируется в журнале.

### Товары, склад и себестоимость

- Управляющий/владелец задаёт товару себестоимость и цену продажи отдельно. Интерфейс показывает наценку и маржу; цена продажи не пересчитывается автоматически.
- При поступлении товара создаётся партия с количеством и закупочной себестоимостью. Если цена закупки не изменилась, можно использовать прежнюю; если изменилась — ввести новую. История партий сохраняется.
- Списание себестоимости проданного товара считать по FIFO: вначале расходуется самая ранняя партия с остатком.
- Добавление товара в счёт резервирует/уменьшает доступный остаток. Удаление товара из неоплаченного счёта с причиной возвращает его на склад.
- Возврат уже оплаченной продажи оформлять отдельной операцией возврата/корректировки, не удалять историю.
- Ручные списания, инвентаризация и корректировки склада доступны управляющему/владельцу, требуют причины и аудита.
- В карточке товара показывать текущий остаток, себестоимость по партиям, цену продажи, валовую прибыль, наценку и маржу.
- Формулы и определения финансовых показателей закрепить отдельно в API/доменном контракте, чтобы отчёты не трактовали маржу и прибыль по-разному.

### Оплата и подтверждение P2P

- На старте нужны наличные и P2P-перевод. Способы оплаты должны настраиваться через админку: добавление/отключение нового метода не должно требовать переписывания бизнес-логики.
- Счёт может быть оплачен несколькими частями и разными методами. Для каждой части хранить сумму, способ, время, кассира и ссылку на подтверждённый P2P перевод, если он есть.
- P2P сценарий должен использовать отдельный Telegram Business аккаунт клуба и отдельную интеграцию/настройки, не зависеть от чужого аккаунта или CRM КАД.
- CRM может показать кассиру подходящее входящее уведомление о переводе по сумме и времени. Кассир вручную связывает уведомление со счётом и подтверждает платёж.
- Скриншот/сообщение клиента сам по себе не подтверждает оплату. CRM не закрывает счёт автоматически: она отображает найденный перевод, а кассир принимает решение и завершает счёт.
- Один P2P перевод нельзя привязать к нескольким счетам. Неоднозначные совпадения показывать кассиру для ручного выбора.
- Если интеграция Telegram Business не предоставляет надёжный машинный доступ к факту перевода, система должна явно показывать неподтверждённый статус, а не имитировать банковское подтверждение.

### Смены, касса и расходы

- При открытии смены кассир вводит фактический остаток наличных в кассе.
- В течение смены кассир видит свою выручку по способам оплаты, список счетов, расходы и ожидаемую сумму наличных.
- При закрытии смены кассир вводит фактический пересчёт наличных. Система показывает расчётную сумму, фактическую сумму и расхождение.
- Кассир может записывать расходы смены. Нужны сумма, категория, способ оплаты, время, комментарий/причина; расходы, оплаченные из кассы наличными, уменьшают ожидаемый остаток кассы.
- Владелец/управляющий вручную вводит регулярные и прочие расходы (зарплата, коммунальные услуги, аренда и т. п.). Автоматические банковские импорты и расчёт зарплаты в первую версию не входят.
- Любая финансовая корректировка, возврат, отмена и расхождение требуют причины. Нельзя бесследно удалить финансовую запись.
- В отчётах раздельно показывать выручку, себестоимость проданных товаров, валовую прибыль, расходы, чистый результат и расхождение смены. Не смешивать денежный остаток кассы с прибылью.

### Журнал и отчёты

- Неизменяемый журнал аудита: пользователь, время, объект, действие, причина и значения до/после для значимых правок.
- Владелец и управляющий могут открыть любой счёт и увидеть кабинет, время, товары, начисления, платежи, кассира, предчек, возвраты и всю историю изменений.
- Кассир видит свои заказы и показатели текущей/закрытых смен согласно правам.
- Предусмотреть отчёты по дням и периодам: оборот и оплаты по методу, продажи товаров, FIFO-себестоимость, валовая прибыль, расходы и сверка смен.

### Клиенты и QR-коды отзывов

- В счёте можно необязательно сохранить имя и телефон клиента. Эти поля не обязательны; структура данных должна позволить позже добавить бонусы, промокоды и историю визитов.
- В первой версии нет программ лояльности, скидки за отзыв или отдельного приложения для клиентов.
- Владелец/управляющий может хранить ссылки на страницы отзывов (например, Yandex и 2GIS) и получать печатный QR-код. QR ведёт на страницу отзыва; скидки за отзыв не начисляются.

## Статусы счёта (предлагаемый контракт)

1. **Черновик** — счёт создан, таймер не запущен.
2. **Идёт игра** — таймер запущен; товары можно добавлять.
3. **Ожидает оплаты** — таймер остановлен предчеком; оплату можно внести полностью или частями.
4. **Оплачен / закрыт** — принята полная сумма, закрытие подтверждено кассиром.
5. **Отменён / возвращён** — отдельное компенсирующее событие с причиной и правом доступа.

Переходы и допустимые действия для каждого состояния закрепить в доменном слое и API, а не только скрывать кнопки интерфейса.

## План реализации

1. **Подготовка контракта:** зафиксировать модель данных, роли/права, состояния счёта и смены, правила округления, FIFO, журнал, оплаты и API. Отдельно согласовать неясные исключения до их кодирования.
2. **Frontend первым:** собрать адаптивный web/PWA-интерфейс на типизированных mock-данных: вход, рабочее место кассира, кабинка/таймер, состав счёта, предчек, оплата, смена, расходы; затем админка каталога, склада, тарифов, пользователей и отчётов. Сразу описывать ожидаемые запросы в OpenAPI-контракте.
3. **Backend:** реализовать Django API и PostgreSQL схему по согласованному контракту: авторизация и права, доменные операции счетов, неизменяемый аудит, FIFO партии, оплаты/возвраты, смены, расходы и отчёты. Денежные операции должны быть транзакционными и защищёнными от повторной отправки.
4. **Интеграция:** подключить web-клиент к API; затем PWA очередь офлайн-действий с безопасной синхронизацией и разрешением конфликтов. После проверки доступности Telegram Business данных — подключить P2P адаптер и тестовые уведомления.
5. **Мобильное приложение:** подключить Expo Android/iOS к тому же API после стабилизации серверного контракта; не дублировать правила расчёта в приложении.
6. **Проверка и запуск:** проверить сквозные сценарии, права, аудит, восстановление резервной копии, развёртывание на VPS и дальнейший перенос на локальный сервер.

## Обязательные сквозные сценарии проверки

- Открытие смены → создание счёта → запуск таймера → добавление/удаление товара → предчек → оплата наличными и P2P частями → закрытие → проверка чека и отчёта.
- Изменение закупочной цены товара → поступление новой партии → продажа остатков по FIFO → корректное восстановление остатков при отмене позиции.
- Закрытие смены с расходом наличными → расчёт ожидаемого остатка → ввод фактической суммы → видимое расхождение.
- Возврат или финансовая правка с обязательной причиной → запись аудита → проверка истории управляющим.
- Потеря сети во время работы → повторная отправка без дублирования заказа/платежа → синхронизация после восстановления связи.
- Неподтверждённый или неоднозначный P2P перевод не должен закрывать счёт.

## Границы первой версии

В первую версию не входят: бронирование, программа лояльности, клиентское мобильное приложение, автоматический импорт расходов, автоматическое закрытие счета по уведомлению о переводе и полноценная работа P2P без интернета. Сначала запускается online-версия с ограниченной устойчивостью кассы к кратким перебоям связи.

## P2P онлайн-этап

Уведомление → доверенное банковское событие → подсказка кассиру. Оно не создаёт оплату и не закрывает счёт. Кассир задаёт ожидаемую часть/карту, проверяет найденный перевод, подтверждает обычную оплату; затем отдельно закрывает полностью оплаченный счёт. Uzcard и Humo настраиваются независимо, пустая allowlist/Business connection оставляет источник неподключённым. Настройка, ограничения сумм/ручной проверки и защита повторов: [P2P](docs/P2P.md). Проверка на Django/PostgreSQL: [ONLINE_MVP](docs/ONLINE_MVP.md).

### Выбор PlayStation при открытии счёта

При открытии счёта кассир выбирает свободную кабинку и тариф PS3, PS4 или PS5; таймер начинается сразу. Счёт сохраняет приставку и цену часа, поэтому последующие изменения тарифа не меняют расчёт открытых и закрытых счетов. Для ранее созданных счетов миграция сохраняет исходную цену счёта; название приставки и ссылка на тариф восстанавливаются из текущих данных связанной кабинки, если они сохранились.

После миграций команда `python manage.py init_club` создаёт отсутствующие тарифы и кабинки 1–7, сохраняя существующие цены. При дубликатах или других активных кабинках она отменяет изменения и требует ручной проверки. Перед запуском на действующей базе необходимо создать резервную копию, проверить связанные счета и только после этого отключить либо удалить неподходящие кабинки согласно правилам хранения истории.
