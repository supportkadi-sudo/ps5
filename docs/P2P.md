# Uzcard / Humo через Telegram Business

Этот поток использует обычные входящие переводы от двух разных банковских Telegram-ботов. Paynet/Cash, клиентские скриншоты, прямые сообщения и пересылки не участвуют. Клуб использует свои настройки; KADI не является runtime-зависимостью.

## Три независимых состояния

1. **Доверенное событие (`verified_source`)** — HMAC верен, фактический Telegram `from_user.id` входит в allowlist выбранного источника, `is_bot=True`, Business connection точно совпадает с настройкой. Это доверие к происхождению сообщения, а не признание оплаты.
2. **Совпадение (`found`)** — ровно одна ожидаемая часть с точной суммой, источником, последними четырьмя цифрами карты и временным окном. Сохраняются только подсказки при чтении; уведомление не меняет счёт или платежи.
3. **Принято кассиром (`accepted`)** — явный `AcceptPayment` с `confirmedByCashier=true`; обычная Payment с уникальной ссылкой на Transfer, кассиром, методом и сменой. Даже полная оплата оставляет `awaiting_payment`. Только отдельный `CloseAccount` закрывает полностью оплаченный счёт.

Кассир формирует предчек, выбирает настроенную карту и ожидаемую часть, нажимает «Ожидать перевод». После «Перевод найден» проверяет сумму/карту/время и нажимает «Подтвердить оплату». Остаток можно принять другим методом; закрытие отдельно. Ожидание не является платежом или резервированием денег.

## Конфигурация реального клуба

В `.env` задайте `P2P_WEBHOOK_SECRET` случайным отдельным секретом и `P2P_BOT_TOKEN` собственного интеграционного бота клуба. Для **каждого** источника задайте независимый `P2P_UZCARD_SENDER_IDS` / `P2P_HUMO_SENDER_IDS` (положительные numeric `from_user.id`, через запятую) и `P2P_UZCARD_BUSINESS_CONNECTION_ID` / `P2P_HUMO_BUSINESS_CONNECTION_ID`. Пересечение sender allowlist запрещено. Не используйте username, chat ID или ID владельца аккаунта вместо ID банковского бота. Не копируйте credentials KADI.

Настройки → Оплата: создайте метод типа P2P, выберите Uzcard/Humo и введите только последние 4 цифры карты. Полный PAN не требуется. Устаревший P2P метод без источника/карты нельзя использовать для ожидания или приёма банковского события.

После миграций на согласованном окружении:

```bash
docker compose --profile p2p up -d p2p-bridge
# Без Docker, из backend, с настроенным окружением:
python manage.py run_p2p_bridge
```

Один экземпляр polling на bot token; webhook этого бота должен быть отключён владельцем перед выбором polling. Команда сама webhook не удаляет. `P2P_BACKEND_URL` должен вести к backend через доверенную внутреннюю сеть или HTTPS. Compose использует `http://api:8000` внутри сети контейнеров. Не выставляйте bridge/database наружу. Backend не использует Telegram token для проверки уведомлений: подписанный канал от bridge — граница доверия, этот секрет даёт возможность утверждать provenance и должен быть защищён.

До live-подключения проверить доставку именно сообщений **обоих** банковских ботов в club Business connection. Наличие Business-подписки не доказывает доступность этих уведомлений через Bot API. Верифицировать реальные sender IDs и connection ID по фактическим Telegram updates без публикации текста/карты/токенов. Если Telegram не доставляет эти сообщения, источник остаётся недоступен — ручная вставка сообщения не заменяет его. В UI «настроен» означает заполненную конфигурацию backend, а не проверенную связь с Telegram; отдельная пометка требует проверки связи.

## Приём и повторы

`run_p2p_bridge` принимает только новые `business_message` с текстом, проверяет фактического sender, bot flag и connection, отклоняет forward/via_bot/edit/photo. Source определяется по независимым ID отправителей, не по содержимому текста. Никакого admin-paste fallback. Backend повторяет проверки provenance.

`POST /api/v1/integrations/telegram-business` использует только HMAC, а не browser session. `X-P2P-Signature = v1=<hex HMAC-SHA256(secret, v1 + LF + timestamp + LF + exact_body)>`, `X-P2P-Timestamp` — Unix seconds; допустимое отклонение ±300 секунд. JSON содержит source, senderId, senderIsBot, businessConnectionId, chatId, messageId, text (OpenAPI). HMAC и стабильная identity повторяют подход [KADI bridge](https://github.com/supportkadi-sudo/Kadi-2.0/blob/2738afad70949bb58a6e3c1d7a0eeac6ed773fbf/bot/p2p_bank_bridge.py) и [signature](https://github.com/supportkadi-sudo/Kadi-2.0/blob/2738afad70949bb58a6e3c1d7a0eeac6ed773fbf/bot/services/webhook_signatures.py); маршрутизация Paynet/Cash и автоматическое зачисление KADI не перенесены.

Event ID = SHA256 JSON-тройки `(Business connection, chat ID, message ID)` с префиксом `tg-business:`. Unique constraint не зависит от source. Повтор того же события возвращает прежний UUID; изменённая нормализованная сумма/карта/время/источник — 409. Баланс на карте не относится к transfer payload и не сохраняется. Редактирования не подписываются bridge как новые переводы. Payment.transfer — OneToOne, подтверждение проходит существующий durable command receipt и version/DB locks.

Bridge подтверждает Telegram offset только после backend acknowledgement. Временная ошибка повторяется с timeout 15 секунд и паузой до 30 секунд; повтор после перезапуска безопасен. Unsupported message (400) пропускается с обезличенным предупреждением. 403/409 и сетевые ошибки блокируют продвижение до устранения причины; следите за логом/очередью. Это намеренный fail-closed; Telegram хранит необработанные updates ограниченное время (длительную недоступность нужно сверять с банковской историей). Нет отдельного постоянного raw-text outbox или гарантии восстановления после исчерпания хранения Telegram.

Сохраняются точная сумма `Decimal(18,2)`, последние 4 цифры, время операции, источник, ID события и статус происхождения. Текст/остаток/полный PAN/скриншот не хранятся и не логируются. API отдаёт банковскую сумму десятичной строкой; старый mock может возвращать integer. История и workspace доступны только вошедшим сотрудникам; cashier ограничен своей сменой/платежами, owner/manager видят общий журнал. UI показывает `****last4`.

## Сопоставление и ограничения

`ExpectTransfer` требует session, CSRF, Idempotency-Key, актуальную версию, открытую разрешённую смену, предчек, доступный P2P метод и положительную часть не выше остатка. Одна текущая ожидаемая часть на счёт; изменение журналируется, повтор UUID не меняет ожидание. После приёма часть погашается; для следующего P2P перевода нужно новое ожидание.

Окно ожидания — 30 минут; банковский timestamp может быть до двух минут раньше создания ожидания из-за минутной точности/порядка прихода. Проверяется время создания счёта, будущие события более минуты не подходят. Совпадение пересчитывается сервером при отображении и при подтверждении. Несколько кандидатов, несоответствие суммы при существующем ожидании или неполные данные → `manual_review`; отсутствие кандидатов → `unmatched`. Отключённый источник/метод, истёкшее ожидание и изменённая карта не дают принять оплату. Несопоставленные уведомления видны в списке; история доступна постранично через `/transfers`.

Неоднозначные события нельзя принудительно принять в MVP: управляющий сверяет банковскую историю/счета, устраняет ошибочные ожидания и повторяет проверку. Отдельного bypass «верю скриншоту» нет. В списке нет чужих candidate account IDs для cashier.

**Тийины:** существующая касса принимает целые UZS. Уведомление `992.56` сохраняется точно, но не округляется до 993/992 и не создаёт платёж; остаётся ручная проверка. Пример Humo `249.402,00` — целые 249402, может совпасть с такой ожидаемой частью. Для автоматического сопоставления переводите ровно заказанную целую сумму. Поддержка дробных кассовых оплат потребует отдельного изменения финансового контракта, отчётов/возвратов. Это ограничение пилота, если клуб реально принимает дробные суммы.

Реальные credentials и Telegram Business доставка в рамках разработки **не проверены**. HTTPS, пароли, backup/restore, начальные остатки и наблюдение на месте остаются обязательными условиями денежного пилота. Проверки с синтетическими событиями описаны в ONLINE_MVP.md.
