# API v0.1 — frontend-first proposal

`contracts/openapi.json` is the single request/response schema. Generate client types with `cd frontend && npm run generate:api`. On the Django stage drf-spectacular will export this contract; CI must detect incompatible changes. No hand-maintained duplicate DTOs. Mobile imports generated types, never mock calculations.

Login first obtains a CSRF cookie/token through GET /auth/csrf, then rotates the token on authentication. Commands use session cookies, CSRF and UUID Idempotency-Key scoped to actor and endpoint. Store the request hash and response atomically: same key/body returns original response; different body returns 409. Account commands require expectedVersion; stale version returns 409 and requires reload. Errors have code/message/fieldErrors. Workspace is an MVP bounded club read model; pagination and report date filters remain server responsibilities as history grows.

Money is integer UZS, capped at JS safe integer. No floating monetary arithmetic. Timer calculation proposal: sum elapsed seconds across segments, multiply hourly snapshot using integer arithmetic, divide by 3600 only at final calculation, round total including goods to nearest 500; exact midpoint rounds upward. No minimum fee. Display elapsed minutes; seconds are retained so repeated pause/resume cannot discard time. These boundary choices require owner confirmation before backend billing implementation.

Create → draft; start → playing; precheck → awaiting_payment (stops segment); resume → playing; payment only while awaiting_payment; close only awaiting_payment with confirmed paid == total. Full payment alone does not close. No overpayment. Resume after a partial payment is allowed, preserving payments. Product edits after partial payment are blocked in this prototype; refund policy must be agreed before enabling them. Draft/playing/awaiting without payments can change goods. Closed financial history cannot be edited.

FIFO allocations reserve oldest available batch on adding goods, snapshot cost/price, and restore the exact original allocations on reasoned removal. Report COGS is recognized on account closure. Revenue = closed-account totals; gross profit = revenue − COGS; net result = gross profit − manually entered expenses. Cash movement separately uses accepted payments even for still-open accounts. Margin = (price − cost)/price; markup = (price − cost)/cost; zero denominator → undefined. Expenses recognized on entered date. Expense scope is explicit: shift expenses affect the cashier drawer; club expenses are paid outside that drawer and require manager/owner. Reports filter inclusive dates in Asia/Tashkent. Rent including utilities must not be entered twice.

Cashier: own shift/accounts, payments, own expenses; no cost, stock or settings access. Manager/owner: all accounts, reports, catalog, batches, tariffs, methods, reviews. Owner: user roles. Refund/payment reversal/closed-account correction are deliberately unavailable until permissions and compensating entries are agreed. Stock adjustment requires manager/owner and reason. Accounts survive shift closure and are assigned to next shift with audit; payment belongs to shift where received.

P2P notifications have explicit evidence state. Fixtures use verified_fixture, visibly marked demo; unverified/ambiguous are never accepted. Link and acceptance are one explicit cashier command; transfer is unique across accounts. Real backend must replace fixtures with verified source events from a separate club Telegram Business account; adapter unavailable means manual review, never fabricated success.

Offline: stage 1 caches app shell and persists mock sandbox locally. Mutations are blocked when browser reports offline; no payment/closure queue. This intentionally avoids inventing an unapproved cash offline policy. There are no unsynchronized server records in this stage; local data is always labeled DEMO. Stage 2/3 durable outbox requires separate approval of permitted commands, stock conflicts, timestamps and reconciliation. Network errors must retain pending command key for safe retry.

Backend remains unimplemented in this PR. Mock authorization/idempotency/FIFO only exercise UX and contracts, and are not production security or DB guarantees.

Report.productSales is authoritative for the selected period: productId, snapshot name, quantity, unrounded goods revenue and FIFO costOfGoods. It is computed from the full server/mock history, never from the bounded workspace. A removed line is excluded. Zero-sales products are omitted.

The frontend persists one unresolved command DTO and UUID per actor before sending. Explicit retry after reload uses the original body and key; a new command cannot replace it. Only a validated success or definite validated 400/401/403/404/405/422 rejection clears it. Conflict, timeout, malformed acknowledgement and 5xx retain it for retry/reconciliation; there is no automatic key reset or unsafe discard. Credentials/CSRF are reacquired by authentication and are not stored in this record. Browser storage is not a production trust boundary.
