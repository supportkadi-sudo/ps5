# API v0.2 — contract-first Django and frontend mock

`contracts/openapi.json` is the single request/response schema. Generate client types with `cd frontend && npm run generate:api`. Django validates commands against this same JSON Schema and exports it via GET /api/v1/schema. TypeScript and DRF share one contract-first source. Route/response tests plus generated DTO drift checks detect disagreement. No hand-maintained duplicate DTOs. Mobile imports generated types, never mock calculations.

Login first obtains a CSRF cookie/token through GET /auth/csrf, then rotates the token on authentication. Commands use session cookies, CSRF and UUID Idempotency-Key unique across all commands for an actor; endpoint participates in the request identity. Store the request hash and response atomically: same key/body returns original response; different body returns 409. Account commands require expectedVersion; stale version returns 409 and requires reload. Errors have code/message/fieldErrors. Workspace is an MVP bounded club read model; pagination and report date filters remain server responsibilities as history grows.

Money is integer UZS, capped at JS safe integer. No floating monetary arithmetic. Server timer rule: sum elapsed microseconds across persisted server segments, ceil the cumulative duration to started minutes once, multiply the hourly snapshot with exact integer/rational arithmetic, and round the bill including goods to nearest 500; exact midpoint rounds upward. No minimum fixed fee. No per-segment or per-minute money rounding. `gameAmount` is the integer display part of the rational game charge; total remains authoritative. Mock v0.1 still uses seconds and is explicitly not the production calculator. Boundary tests and examples: BACKEND_STAGE.md.

Create → draft; start → playing; precheck → awaiting_payment (stops segment); resume → playing; payment only while awaiting_payment; close only awaiting_payment with confirmed paid == total. Full payment alone does not close. No overpayment. Resume after a partial payment is allowed, preserving payments. Product edits after partial payment are blocked in this prototype; refund policy must be agreed before enabling them. Draft/playing/awaiting without payments can change goods. Closed financial history cannot be edited.

FIFO allocations reserve oldest available batch on adding goods, snapshot cost/price, and restore the exact original allocations on reasoned removal. Report COGS is recognized on account closure. Revenue = closed-account totals; gross profit = revenue − COGS; net result = gross profit − manually entered expenses. Cash movement separately uses accepted payments even for still-open accounts. Margin = (price − cost)/price; markup = (price − cost)/cost; zero denominator → undefined. Expenses recognized on entered date. Expense scope is explicit: shift expenses affect the cashier drawer; club expenses are paid outside that drawer and require manager/owner. Reports filter inclusive dates in Asia/Tashkent. Rent including utilities must not be entered twice.

Cashier: own shift/accounts, payments, own expenses; no cost, stock or settings access. Manager/owner: all accounts, reports, catalog, batches, tariffs, methods, reviews. Owner: user roles. Backend full RefundAccount is restricted to owner/manager with reason, open issuing shift and explicit restockGoods. Original payments/lines remain; append-only Refund and PaymentReversal compensate them. Partial refunds, arbitrary closed-account edits and changing refund method are unavailable. Stock adjustment requires manager/owner and reason. Accounts survive shift closure and are assigned to next shift with audit; payment belongs to shift where received.

P2P notifications have explicit evidence state. Fixtures use verified_fixture, visibly marked demo; unverified/ambiguous are never accepted. Link and acceptance are one explicit cashier command; transfer is unique across accounts. Real backend must replace fixtures with verified source events from a separate club Telegram Business account; adapter unavailable means manual review, never fabricated success.

Offline: stage 1 caches app shell and persists mock sandbox locally. Mutations are blocked when browser reports offline; no payment/closure queue. This intentionally avoids inventing an unapproved cash offline policy. There are no unsynchronized server records in this stage; local data is always labeled DEMO. Stage 2/3 durable outbox requires separate approval of permitted commands, stock conflicts, timestamps and reconciliation. Network errors must retain pending command key for safe retry.

The first Django/PostgreSQL server slice is implemented separately from PR #2. Operations marked x-backend-implemented are real; Employee and review endpoints now use server SaveEmployee/SaveReviewLink DTOs; the old SaveUser/SaveReview schema names are retained solely for the unchanged mock. Mock authorization/idempotency/FIFO are not production guarantees. See BACKEND_STAGE.md for exact scope and verification.

Report.productSales is authoritative for the selected period: productId, snapshot name, quantity, unrounded goods revenue and FIFO costOfGoods. It is computed from the full server/mock history, never from the bounded workspace. A removed line is excluded. Zero-sales products are omitted.

The frontend persists one unresolved command DTO and UUID per actor before sending. Explicit retry after reload uses the original body and key; a new command cannot replace it. Only a validated success or definite validated 400/401/403/404/405/422 rejection clears it. Conflict, timeout, malformed acknowledgement and 5xx retain it for retry/reconciliation; there is no automatic key reset or unsafe discard. Credentials/CSRF are reacquired by authentication and are not stored in this record. Browser storage is not a production trust boundary.

## Backend acknowledgement and read model

Django commands return `CommandResult {entityId,operation,version}` atomically stored with the command. A replay returns the original acknowledgement, never an old privileged Workspace. The temporary response union also permits Workspace for the existing mock; the frontend HTTP adapter is **not connected** in this backend PR and requires the explicit integration steps in BACKEND_STAGE.md. Schema/DTO changes do not make the existing HttpApi production-compatible by themselves.

Workspace and reports use a single read-only REPEATABLE READ transaction. Cashier cost fields are redacted; batches/audit payload are absent, own shifts/accounts/expenses only. Workspace is bounded; full history uses signed cursor pages documented in BACKEND_STAGE.md. `GET /health` and `/ready` are public; schema/workspace/report require authentication.

Refunds are recognized on the issuing date, so revenue, COGS and net method aggregates may be negative for a period. ProductSales retains gross closed-account sales; returned revenue/cost is separately reflected in the aggregate result. This avoids rewriting old sales periods. A cancelled/refunded account retains original `paid` and payment history; audit contains its compensating refund. Full refund confirms money already handed back by the manager; it never calls a bank.


## Server completion contracts

Every implemented session POST declares required X-CSRFToken; domain POSTs also require Idempotency-Key. DRF validation resolves the request DTO from the endpoint's actual OpenAPI definition, not a handwritten parallel serializer. Employee/review commands require version and reason; manager can administer cashiers only, owner can administer all except removal of last active owner. Password commands are write-only, HMAC-hashed for receipts, never persisted as raw DTO/outbox and invalidate old sessions. Login rate limits are PostgreSQL-based; 429 has Retry-After.

History pages use `{items,nextCursor}` with signed actor/role/resource/filter-bound timestamp/UUID cursors. Workspace subsets are explicitly not historical totals. Account detail retains initial payments and optional Refund with compensating reversal references. Shift method totals and Product.availableStock are authoritative full-DB aggregates. Reports remain the existing period API with gross productSales and separate net refund effects. See BACKEND_STAGE.md for exact limits, operational assumptions, TLS/DB/backup requirements and frontend connection order.
