## Зависимости

Первый `npm audit` сообщил три затронутых пакета в **dev-зависимостях**: Vitest, @vitest/mocker, tinypool. Severity в npm — moderate/critical; это не доказательство доступной атаки на production-CRM. Сценарии соответствующих advisories зависят от доступного mock/dev-сервера либо предварительного prototype pollution в worker options. Production-сборка не публикует тестовый сервер.

Vitest обновлён до 5.0.5; повторная проверка npm audit — **0 известных уязвимостей** во всём дереве установленных зависимостей на момент проверки. Источники: [Vitest advisory](https://github.com/vitest-dev/vitest/security/advisories/GHSA-82fw-gwwq-j7x9), [tinypool advisory](https://github.com/tinylibs/tinypool/security/advisories/GHSA-5gmw-xhrv-c9v3). AJV добавлен для реальной runtime-проверки по уже существующему контракту.

## Оставшиеся границы безопасности

- Это frontend-first демо. Пароль `demo`, роли и все данные доступны владельцу браузера через DevTools/localStorage. Скрытие себестоимости в mock-ответе не защищает её от человека с доступом к этому браузеру. Здесь нельзя хранить настоящие персональные или платёжные данные и вести реальную кассу.
- Mock receipts теперь сохраняются вместе с локальным Workspace, а pending-команда — отдельно до результата. Это не защищённое серверное хранилище: PostgreSQL должен сохранять ключ, hash и результат транзакционно с деньгами/складом.
- Обнаружение устаревшей вкладки защищает обычные последовательные записи, но localStorage не имеет атомарного compare-and-swap между процессами. Демо допускает одну рабочую вкладку; конкурентные кассы требуют backend-блокировок.
- P2P — явно помеченные fixtures. Ни достоверный источник Telegram Business, ни реальная авторизация, неизменяемый серверный аудит, возвраты и DB-транзакции ещё не реализованы.
- Нулевой npm audit не означает отсутствия неизвестных уязвимостей. Проверка не включает production-инфраструктуру, которой пока нет.

Исправления продолжают PR #2 поверх `6b16820b5c8a125e82a51228f4ff4c472591a9eb`. Отдельный backend не добавлялся.

| Замечание | Изменение владельца поведения | Регрессия |
|---|---|---|
| P1: потеря ключа при reload/другой команде | `PendingCommands` сохраняет исходный DTO и UUID **до** отправки, отдельно по сотруднику. Новая команда не заменяет неразрешённую. Для честного повторения в демо mock-idempotency receipts сохраняются атомарно **в той же localStorage-записи**, что и Workspace. Старая запись Workspace читается без удаления истории; отсутствующая разбивка старого производного report мигрируется, затем пересчитывается. Это локальная имитация серверного журнала, не гарантия PostgreSQL. Ошибка сохранения не коммитит новое состояние; ошибка удаления pending не даёт автоматически новый ключ. Демо по-прежнему рассчитано на одну рабочую вкладку; backend должен обеспечить транзакции и защиту конкурентных касс.

Защита `requestEpoch` сохранена. Pending не означает серверное подтверждение оплаты/закрытия; offline-команды не отправляются и не подтверждаются. API/auth-ответы не попадают в app-shell cache. Новые регрессии не заменяют и не ослабляют прежние сценарии.

Формат локального демо-хранилища теперь version=1 с workspace и receipts. Для отката к старой версии сначала экспортируйте демо-запись; старый код не умеет читать envelope. Не очищайте хранилище для обхода ошибки и не стирайте pending при неразрешённом результате. Серверная сверка/разрешение конфликтов остаётся задачей backend-этапа.

Результаты локального прогона: `npm run check:contract` — без drift; `npm test` — 38 tests / 7 files; `npm run build` — успешно; `npx playwright test --workers=2` — 20/20 (desktop/mobile, включая старый polling regression и оба каталога). Скриншоты из повторного технического прогона не включаются в исправления: они генерируются тестами и доступны как CI artifacts; оформление не перерабатывается. Полный diff проверяется относительно предыдущего head PR, включая staged generated types.
