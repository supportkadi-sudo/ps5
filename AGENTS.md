# Правила агента — CRM игрового клуба

Перед любой задачей прочитай этот файл и соответствующие разделы `README.md` и `ARCHITECTURE.md`. Эти документы описывают требования и целевую архитектуру; если они расходятся с реальным кодом, сначала проверь источник истины и зафиксируй противоречие.

## 1. Работай от проблемы и первопричины

До написания кода:

1. определи пользовательскую или бизнес-проблему;
2. найди владельца поведения в текущем коде и проследи полный поток данных;
3. проверь существующие модули, контракты, миграции и тесты;
4. сформулируй ожидаемое поведение и инвариант;
5. оцени риски и самый простой обратимый вариант.

Не соглашайся автоматически с идеей только потому, что её предложили. Если функция создаёт лишние расходы, сложность, денежный риск или не решает подтверждённую проблему, объясни это и предложи конкретную альтернативу. Окончательное продуктовое решение принимает владелец.

Не добавляй framework, сервис, очередь, кэш или отдельный runtime ради гипотетического масштаба. Стартовая архитектура — модульный монолит. Микросервис выделяется только при доказанной необходимости.

## 2. Исправляй первопричину, не накладывай патч поверх патча

Запрещено прятать дефект новым локальным обходом:

- новый CSS override вместо исправления исходного стиля;
- дублирующий компонент/сервис вместо исправления существующего владельца поведения;
- дополнительный условный оператор вместо починки неверного состояния;
- повторная обработка данных на UI, чтобы компенсировать неверный API-контракт;
- копия функции с небольшими отличиями;
- новая настройка или скрипт, дублирующие существующий источник конфигурации.

Найди слой, которому принадлежит поведение, исправь его и удали устаревший обход в том же изменении. Если удалить обход сразу нельзя, объясни причину, зафиксируй владельца и отдельную задачу с условием удаления. Скрытые временные решения запрещены. Для bugfix сначала добавь воспроизводящий регрессионный тест, затем исправляй.

## 3. Не делай монофайлы и не дроби без пользы

Один модуль — одна понятная ответственность. Не смешивай в одном файле UI, HTTP-запросы, бизнес-расчёты, прямую работу с БД, внешние интеграции и форматирование.

- Не создавай гигантские `views.py`, `models.py`, `serializers.py`, `services.py`, React-экраны или файлы с несколькими несвязанными доменами.
- Разделяй код по use case/домену, когда у частей разные обязанности или независимые тесты.
- Не создавай пустые абстракции, универсальные factory/repository-слои и сотни файлов на пару строк без конкретной причины.
- Не создавай микросервисы из модулей одного продукта. Общая транзакция по счёту, оплате, складу и аудиту должна оставаться под контролем одного backend.
- Если файл становится трудно читать или тестировать, раздели его до добавления следующей крупной функции.

## 4. Соблюдай границы слоёв

### Backend — Django REST Framework

- API view/viewset отвечает за HTTP, авторизацию, валидацию границ и вызов use case; не содержит основной бизнес-логики.
- Serializer/schema определяет входной/выходной контракт, но не является хранилищем бизнес-правил.
- Сервис/use case выполняет бизнес-операцию и управляет транзакцией.
- Django model описывает persistence и ограничения; не используй модель как случайный публичный API-контракт.
- Интеграционный client отвечает за протокол внешней системы; преобразование внешнего статуса в доменное состояние находится отдельно.
- Фоновые задачи, если они понадобятся, вызывают тот же сервис, а не копируют бизнес-логику.
- Схема PostgreSQL меняется только миграциями Django; миграция должна безопасно учитывать уже существующие данные.
- Не добавляй Celery/Redis до появления реального фонового сценария с обоснованными гарантиями доставки.

### Web/PWA — React + TypeScript

- Страница собирает экран из feature-компонентов; не содержит весь рабочий процесс.
- Компоненты отображения не делают прямые `fetch` и не пишут напрямую в IndexedDB.
- HTTP-вызовы находятся в API-слое; состояние и преобразования конкретного процесса — в его feature/model/service.
- Общие UI-компоненты не зависят от конкретного бизнес-раздела.
- Серверные данные не копируются без необходимости во второй глобальный store.
- TypeScript-типы клиента должны происходить из OpenAPI-контракта, а не вручную расходиться с backend.
- Стили исправляй в исходном компоненте/токене, не добавляй каскадный «пластырь» в конец файла.

### Android/iOS

- Expo-клиент использует тот же backend и API-контракт.
- Не копируй расчёт времени, округления, FIFO, прав и статусов в мобильный клиент.
- Реализуй мобильный клиент отдельным этапом после стабилизации API; не создавай заготовочные пустые приложения ради галочки.

## 5. Один источник истины

- PostgreSQL/backend — источник истины для пользователей, ролей, тарифов, цен, счетов, оплат, склада, смен, расходов и аудита.
- Backend рассчитывает суммы, права, FIFO и допустимые переходы состояний. Frontend не может подтвердить перевод, изменить цену в обход API или объявить счёт оплаченным.
- OpenAPI — контракт backend с клиентами. Не поддерживай параллельные несогласованные описания request/response.
- PWA offline outbox содержит только ещё не принятые сервером действия и явно показывает статус синхронизации; он не становится второй постоянной базой.
- Настройки окружения передаются через переменные среды и документируются в `.env.example`; не дублируй их hardcoded-константами.

## 6. Денежные, складские и временные инварианты

Любое действие, меняющее деньги, склад или итог счёта, считается критическим.

- UZS храни целыми сумами либо точным decimal; никогда не используй binary float.
- Цена и сумма пересчитываются/проверяются на сервере.
- Денежные операции и движение склада выполняются транзакционно.
- Повторы API-запросов, callbacks и синхронизации защищай idempotency key/уникальным ограничением.
- Конкурирующие изменения одного счёта или остатка сериализуй блокировками/ограничениями БД там, где это требуется.
- Оплаты, возвраты, корректировки и складские движения не удаляй бесследно: добавляй компенсирующую операцию и append-only запись аудита с актором, временем, причиной и изменениями.
- FIFO применяется к себестоимости проданных товаров по партиям; не заменяй его средней себестоимостью без отдельного решения.
- P2P уведомление, скриншот или близкая сумма не равны подтверждённому переводу. Неподтверждённая/неоднозначная оплата не закрывает счёт.
- Время игры и тариф фиксируй на backend с проверяемыми временными отметками; изменение тарифа не должно переписывать уже созданные счета.
- В offline-режиме показывай локальные записи как несинхронизированные. Повторная отправка не должна создавать дубль. Не подтверждай P2P без связи с источником перевода и не показывай окончательное серверное закрытие до синхронизации.

## 7. Ошибки, секреты и интеграции

- Не используй пустые `except/catch`, не проглатывай ошибки и не возвращай «успех» после частичного сбоя.
- Для внешних запросов задай timeout и ограниченные retry; повтор безопасен только при идемпотентной операции.
- Не записывай токены, пароли, полные карточные/платёжные данные и клиентские персональные данные в логи.
- Реальные секреты и данные клиентов не добавляй в git, тестовые fixtures или документацию.
- Если Telegram Business не даёт надёжный доступ к подтверждению перевода, явно оставь интеграцию в неподтверждённом/manual-review состоянии; не симулируй банковский статус.
- Не запускай destructive SQL, удаление volumes или миграцию на реальном сервере в рамках обычной задачи.

## 8. Тесты и проверки

Изменение не готово без проверки, подходящей риску:

- bugfix — тест, который воспроизводит дефект;
- API/use case — contract и service tests;
- деньги, оплаты, возвраты, FIFO — транзакции, повторы/idempotency, rollback и аудит;
- смены/таймер — переходы состояний и граничные минуты/округление;
- offline queue — повторная синхронизация, конфликт, восстановление после перезапуска;
- права — позитивный и запрещённый сценарий;
- миграция — upgrade на отдельной тестовой БД и проверка существующих данных;
- UI — проверка ключевого сценария и ошибок загрузки/сети.

Сначала проверь тесты изменяемого модуля и связанные контракты, затем разумный набор шире. Не запускай весь дорогой набор после каждого изменения без причины. Не удаляй и не ослабляй тест только ради зелёного CI; выясни, сломан ли код или намеренно меняется контракт.

## 9. Рабочий процесс агента

1. Прочитай ТЗ и архитектуру, изучи фактическую структуру проекта и текущую ветку.
2. Составь короткий план конкретного связанного изменения и перечисли риски/неясности.
3. Создай рабочую ветку от актуальной основной ветки; не работай прямо в main.
4. Делай небольшие завершённые изменения. Не смешивай несвязанные функции, косметику и денежную логику в один diff.
5. После изменения проверь тесты затронутых областей и весь diff: `git diff --check`, отсутствие секретов, дублей, оставленного обхода и незапрошенных файлов.
6. Обнови документацию, если меняются контракт, архитектура, запуск или поведение.
7. В PR укажи: цель, исправленный/созданный поток, затронутые модули, удалённый обход, тесты/результаты, риски и rollback.
8. Не сливай PR и не выкатывай проект в production, пока владелец явно не поручил это. Подготовь проверяемый результат и передай его владельцу.

Один PR должен представлять один связанный change set. Сначала держи его draft во время активной реализации; отмечай готовым к review после завершения и проверки, а не для запуска CI после каждого промежуточного коммита. Запускай проверки только для затронутого scope.

## 10. Definition of Done

Задача завершена, когда исправлена первопричина, архитектурные границы сохранены, старый обход удалён или явно оформлен, денежные/складские инварианты защищены, тесты и документация актуальны, секреты не попали в diff, а владелец может понять из PR что изменилось и как это проверить.
