# Архитектура CRM клуба

Статус документа: целевая архитектура первой версии. Web/mock слой реализован; Django/PostgreSQL — следующий этап. Контракт и ограничения прототипа: `docs/API_CONTRACT.md`, `docs/WEB_STAGE.md`. Если решение меняется, обновить этот документ в том же PR, что и код.

## 1. Архитектурное решение

Начать с **модульного монолита**: один Django REST API и одна PostgreSQL база. Web/PWA и будущие Android/iOS клиенты подключаются к одному API. Telegram Business P2P — отдельный интеграционный адаптер к backend, не самостоятельная система расчётов.

Это сознательно проще микросервисов для одной площадки, одного кассира и одной кассы на смену. Не добавлять Redis, Celery, брокер сообщений или Kubernetes, пока не появится конкретная задача, для которой они нужны.

## 2. Схема компонентов

| Компонент | Ответственность |
|---|---|
| React web/PWA | Рабочее место кассира, админка, локальная очередь несинхронизированных действий |
| Django REST API | Авторизация, права, бизнес-операции, расчёт сумм, аудит и OpenAPI |
| PostgreSQL | Постоянные данные и транзакции; главный источник истины |
| Telegram Business adapter | Приём/нормализация доступных уведомлений о переводе; не закрывает счёт |
| Expo Android/iOS (позже) | Мобильный клиент того же API, после стабилизации web/API |
| VPS (первая версия) | Docker Compose: reverse proxy, web build, API и PostgreSQL; переносимый на локальный сервер |

Внешние интерфейсы и API не должны иметь прямого доступа к таблицам. Все изменения проходят через авторизованные backend use case.

## 3. Предлагаемая структура

Структуру создавать постепенно, вместе с реальными функциями. Не создавать пустые модули и не превращать её в набор микросервисов.

```text
backend/
  config/                 # Django settings, root URLs, ASGI/WSGI
  apps/
    access/                # users, roles, permissions
    club/                  # кабинеты, типы приставок, тарифы
    accounts/               # счета, timer segments, bill lines, state transitions
    catalog/                # товары и способы оплаты
    inventory/              # партии, движения, FIFO
    payments/               # платежи, части платежей, P2P match
    shifts/                 # смены, касса, opening/closing count
    expenses/               # расходы и категории
    audit/                  # append-only audit events
    reports/                # финансовые агрегаты и drill-down
    integrations/           # Telegram Business adapter
frontend/
  src/
    app/                     # bootstrap, router, providers
    pages/                   # композиция экранов
    features/
      cashier/               # рабочее место и операции кассира
      accounts/              # счета и таймер
      catalog/               # каталог и товары
      inventory/             # партии/остатки
      shifts/                 # открытие/закрытие смены
      expenses/               # ввод расходов
      payments/               # методы оплаты и P2P matching UI
      reports/                # отчёты/история
      admin/                  # управление пользователями и настройками
    shared/
      api/                    # API client и OpenAPI types
      ui/                     # общие UI primitives
      lib/                    # форматирование/утилиты без бизнес-решений
mobile/                       # Expo приложение; добавлять после web/API
```

Это ориентир, не требование заранее создать все каталоги. В Django допустимо объединить маленькие смежные домены, пока ответственность ясная; нельзя складывать всю систему в один app или один файл.

## 4. Поток одного счёта

1. Web вызывает API для создания чернового счёта.
2. Backend проверяет пользователя, открытую смену и доступность кабинки, создаёт счёт.
3. Кассир явно запускает таймер; backend фиксирует время и тарифный snapshot.
4. Добавление/отмена товара проходит отдельным use case: цена проверяется сервером, движение склада и строка счёта согласуются в транзакции. Удаление требует причины.
5. Предчек завершает текущий timer segment и переводит счёт в ожидание оплаты. Оплата ещё не подтверждена.
6. Backend принимает платежную часть. Для P2P сохраняется ссылка на уникальный подтверждённый перевод; соответствие подтверждает кассир.
7. Закрытие допустимо только когда полная сумма покрыта подтверждёнными оплатами; backend записывает событие закрытия и аудит.
8. Владелец/управляющий видит детализацию счёта и неизменяемую историю.

Идентификаторы счетов, платежей, событий синхронизации и запросов должны быть устойчивы к повторной отправке.

## 5. Ответственность данных и расчётов

Предлагаемые сущности и связи:

- пользователь, роль и permission;
- смена и касса: кассир, opening cash, closing count, итоги оплат/расходов;
- кабинет, тип приставки и версия тарифа;
- счёт, интервалы таймера, позиции счёта, сохранённые цена/тариф/количество;
- товар, закупочная партия, остаток и append-only stock movement;
- способ оплаты, платежные части, P2P source event и связь match;
- категория и запись расхода;
- append-only audit event;
- необязательный клиент и ссылки на QR отзывов.

Все UZS значения — integer сумы или decimal с явным scale, не float. Точный scale, округление до ближайших 500 и момент признания выручки зафиксировать тестируемым контрактом до backend реализации.

Финансовые отчёты должны отдельно считать:
- выручку по закрытым счетам и методу оплаты;
- себестоимость проданных товаров по FIFO;
- валовую прибыль;
- расходы;
- чистый результат;
- движение наличности и расхождение кассы.

Остаток денег в кассе — не прибыль. Неоплаченный предчек не является подтверждённой выручкой. Не меняй определения показателей без обновления API, отчётов и тестов.

## 6. API и контракты

- Backend владеет правилами и итоговыми суммами.
- Для кассира все операции выполняются через DRF API; Django Admin можно использовать как технический инструмент управляющего, но он не заменяет продуктовую админку и права API.
- OpenAPI генерируется из DRF схемы и является контрактом для TypeScript-клиента.
- Входные команды отделяй от read-моделей там, где use case меняет деньги, склад или состояние счёта.
- Изменения платежа, счёта и stock movement должны выполняться атомарно либо оставаться в явном состоянии ручной проверки.
- Схемы API должны поддерживать версии/совместимость; breaking change обновляет web/mobile клиент и тесты в одном change set.

## 7. Работа без сети

Первая поставка онлайн на VPS, но кассовый интерфейс должен подготовить ограниченное продолжение работы при временном обрыве связи:

- PWA может сохранить локальные команды в IndexedDB outbox и показать «ожидает синхронизации».
- Каждая команда имеет UUID/idempotency key, локальное время и время устройства; после синхронизации server timestamp остаётся авторитетным, а расхождение времени видно в аудите.
- Повторная отправка того же UUID должна вернуть тот же результат, а не создать второй счёт, позицию или платёж.
- Нельзя показывать локальный временный статус как подтверждённый сервером.
- P2P-перевод нельзя подтвердить без доступного источника банковского/Telegram события. Офлайн не означает подтверждённую оплату.
- Очерёдность и допустимые действия офлайн (создать счёт, вести таймер, добавлять товар, принимать наличные) требуют отдельного сценарного контракта до включения: конфликт остатков, устройства и недоверенные часы могут повлиять на деньги.
- После восстановления связи backend подтверждает или отклоняет каждую команду; UI показывает ошибки и не теряет очередь до разрешения.

Не вводить широкую event-sourcing/CRDT архитектуру для этого MVP. Реализовать минимальный durable outbox и идемпотентные команды, только после согласования кассового offline-сценария.

## 8. Доставка и среда

Первая поставка: отдельная база CRM в Docker Compose на временном VPS, HTTPS и резервное копирование. Секреты и production данные не входят в репозиторий. Настройки должны позволять перенести тот же compose stack на сервер клуба и ограничить доступ локальной сетью без переписывания бизнес-кода.

P2P adapter — интеграция с отдельными club Telegram Business credentials, проверяемая отдельно. Не предполагать доступ к API/уведомлениям, которого интеграция реально не предоставляет.

## 9. Нерешённые решения до соответствующего этапа

Не блокировать web-макет вопросами, которые можно решить позже. До реализации затронутого backend use case письменно зафиксировать:

- точную матрицу прав на возврат, отмену, изменение закрытого счёта и складскую корректировку;
- тарифные режимы/минимальную оплату, правило округления ничьей и таймерные границы;
- что именно допускается кассиру при offline и как исключить конфликт товаров/счетов;
- как Telegram Business account предоставляет достоверные transfer events для HUMO/Uzcard;
- порядок возврата денег, комиссий и товара после оплаченного счёта;
- формулы маржи/наценки, момент признания расходов и финансового результата.
